## Interpretation

The empty phase queue is insufficient to distinguish:
1. no authenticated peer session,
2. an authenticated session without the White-P application protocol,
3. an application stream that never receives a complete request frame.

It also leaves a test-harness uncertainty: the previous reader changed ownership of the same process `BufferedReader` after the main test thread consumed the `READY` line.

## Diagnostics correction

- Start a single background reader immediately after each child process starts. It alone owns the child's stdout/stderr reader from the first byte.
- The reader completes a `CompletableFuture<String>` when it observes the `READY` record; the test thread awaits that future to obtain the endpoint.
- Store only a fixed allowlist of phase markers, never arbitrary child output. This keeps logs bounded and excludes exception text, peer identifiers, payloads, prompts, capsules and secrets.
- The .NET fixture now emits:
  - `WAITING_FOR_REMOTE_SESSION` before waiting for an authenticated peer,
  - `SESSION_AUTHENTICATED` after `RemotePeerIdentity` becomes available,
  - `APPLICATION_PROTOCOL_READY` after the negotiated White-P protocol reports connected,
  - then the existing `RECEIVED`, `VALIDATED`, and `SENT` phases.
- The test's three-peer request and response correlation assertions remain unchanged.

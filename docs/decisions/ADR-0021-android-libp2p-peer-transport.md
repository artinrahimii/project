# ADR-0021: Android libp2p peer transport

- **Status:** Accepted for the Android TCP/Noise transport adapter and its local authenticated-stream acceptance test. Android-to-Windows product routing and independent-node acceptance remain pending.
- **Date:** 2026-10-30
- **Related task:** T0163; Protobuf runtime compatibility revalidation for T0036.
- **Decision:** Use the maintained JVM libp2p implementation `io.libp2p:jvm-libp2p:1.3.7-RELEASE` on Android for direct TCP, NoiseXX secure-channel negotiation, Mplex streams, canonical PeerId handling and application-protocol negotiation. Do not author custom cryptographic key exchange, signatures, hashes or encryption. Only direct TCP is enabled in this first adapter; QUIC-native and BoringSSL native artifacts are excluded from the Android APK.
- **Peer identity:** Android creates a stable Ed25519 libp2p identity. The private key is encrypted using AES-256-GCM with a non-exportable Android Keystore key. Existing unreadable/corrupt identity data fails closed rather than silently rotating the PeerId. The transport exposes the canonical Android PeerId through a property for a future pairing screen, but no Android screen currently displays it. The Windows trust-store API requires explicit approval; the WPF enrollment UI is not implemented. The Android trust store likewise exposes an explicit-confirmation API but has no application UI caller yet. Therefore no user-facing out-of-band pairing flow is claimed, and the transport only connects to PeerIds already provisioned in the applicable trust stores.
- **Wire compatibility:** The client dials the metadata-only HTTPS rendezvous entry, checks that the returned canonical PeerId and direct TCP multiaddress agree, negotiates `/white-p/peer-message/1.0.0`, then sends the canonical Protobuf request framed by the existing unsigned-varint codec. A response is accepted only from the authenticated remote PeerId and only when requestId, attemptId, modelId and response host identity match the pending attempt.
- **Protobuf runtime compatibility:** jvm-libp2p exposes `protobuf-java` full-runtime generated types. Mixing that dependency with the app's previous `protobuf-javalite`/lite generated classes risks duplicate classes in the Android dex. Android therefore generates the existing canonical application schema against the full `protobuf-java` and `protobuf-kotlin` 4.36.2 runtimes. Wire field numbers, the single canonical `messages.proto`, Kotlin DSL source generation and cross-language byte fixtures remain unchanged; exact CI must revalidate both generated source sets and every Android consumer.
- **Compatibility caveat:** the upstream jvm-libp2p README documents an Android sample and Android compatibility intent, while also stating that it is not aware of production Android users. Unit tests inject a test protector and do not prove hardware-backed Android Keystore behavior on a physical device. A passing APK and local same-library two-peer loopback test are necessary evidence, not a claim of production deployment maturity or .NET/Android wire interoperability. Public-network reachability, NAT traversal, relay, pairing UI and Android-to-Windows inference acceptance remain separate.

# ADR-0021: Android libp2p peer transport

- **Status:** Accepted for Android direct TCP/Noise transport and CI-verified application-protocol interoperability with the Windows .NET libp2p peer fixture. Physical handset-to-installed-host acceptance, public-network reachability and independent-node deployment acceptance remain pending.
- **Date:** 2026-10-30
- **Related tasks:** T0163, T0183 and transport implementation/revalidation under UPD-S1-016; Protobuf runtime compatibility revalidation for T0036.
- **Decision:** Use the maintained JVM libp2p implementation `io.libp2p:jvm-libp2p:1.3.7-RELEASE` on Android for direct TCP, NoiseXX secure-channel negotiation, Mplex streams, canonical PeerId handling and application-protocol negotiation. Do not author custom cryptographic key exchange, signatures, hashes or encryption. Only direct TCP is enabled in this first adapter; QUIC-native and BoringSSL native artifacts are excluded from the Android APK.
- **Peer identity and trust:** Android creates a stable Ed25519 libp2p identity protected by a non-exportable Android Keystore AES-GCM key, and persists explicit peer trust in a separate purpose-protected store. The Android application displays the exact discovered PeerId in its **Before you trust this host** disclosure before storing a trust decision; sending is a separate action and saved trust can be revoked. Windows uses a current-user DPAPI-protected peer trust store and WPF consent/enrollment flow for the exact remote PeerId. The detailed current consent and trust contract is ADR-0018. Earlier statements in the 2026-10-30 baseline that there was no Android/WPF enrollment caller are retained only as historical context and are superseded by ADR-0018's 2026-11-10 implementation review.
- **Wire compatibility:** The client dials the metadata-only HTTPS rendezvous entry, checks that the returned canonical PeerId and direct TCP multiaddress agree, negotiates `/white-p/peer-message/1.0.0`, then sends the canonical Protobuf request framed by the existing unsigned-varint codec. A response is accepted only from the authenticated remote PeerId and only when requestId, attemptId, modelId and response host identity match the pending attempt.
- **Protobuf runtime compatibility:** jvm-libp2p exposes `protobuf-java` full-runtime generated types. Mixing that dependency with the app's previous `protobuf-javalite`/lite generated classes risks duplicate classes in the Android dex. Android therefore generates the existing canonical application schema against the full `protobuf-java` and `protobuf-kotlin` 4.36.2 runtimes. Wire field numbers, the single canonical `messages.proto`, Kotlin DSL source generation and cross-language byte fixtures remain unchanged; exact CI must revalidate both generated source sets and every Android consumer.
- **Android Keystore verification (T0183):** peer-identity and peer-trust wrapping share a reusable, bounded AES-256-GCM protector with distinct purpose aliases, random 96-bit nonces, authenticated version/alias data, and fail-closed handling for a missing or invalid key. Android instrumentation exercises the actual AndroidKeyStore provider on an API 36 emulator, including non-exportability, persistence across store instances, separate aliases, missing-key recovery behavior and tamper rejection. The emulator check validates provider integration; it does not prove TEE/StrongBox backing or physical-device behavior. Room database encryption at rest remains T0184 and is not implied by these key stores.
- **Compatibility and deployment boundary:** the upstream jvm-libp2p README documents Android compatibility intent but does not establish broad production deployment maturity. JVM unit tests inject a test protector; Android instrumentation uses the real AndroidKeyStore provider on an API 36 emulator. Android CI builds the Windows .NET libp2p peer fixture and runs native cross-runtime tests for correlated inference response, single selected peer, sequential next-peer selection after timeout, and cancellation. Those CI tests exercise the Android production runtime and .NET host transport; they are not the physical-device acceptance gate, do not prove arbitrary public-network reachability/NAT traversal, and do not enable relay. The first-release route remains direct-only and reports direct transport failure; no custom cryptography is authored.

## Implementation revalidation — 2026-11-10 (UPD-S1-016)

The earlier baseline wording above is historical. Current source and CI now establish the following:

- The Android production runtime composes the persistent identity store, explicit Android peer-trust store, metadata-only HTTPS rendezvous directory, direct TCP libp2p transport and the actual inference dispatcher.
- The Android trust UI shows the exact PeerId and privacy disclosure before saving explicit trust; trust revocation is available. The Windows UI separately requires owner consent and the exact approved remote PeerId. See ADR-0018.
- `tests/HostLifecycle.Tests/AndroidInteropPeerServer.cs` runs the Windows .NET libp2p transport as a fixture process. Android tests in `Libp2pInferenceRequestTransportTest.kt` exercise authenticated request/response correlation, selecting one peer, trying the next peer only after the previous timeout, and cancellation against this native .NET fixture. `.github/workflows/product-build.yml` builds the fixture and supplies `WHITEP_INTEROP_SERVER_DLL` to the Android JVM test job.
- The current product Android test job on V 3.1.176 passed 234 tests, with zero failures and one intentionally skipped non-loopback LAN emulator test. The fixture-based .NET interop tests are part of the passed JVM suite. This is CI fixture interoperability, not a physical Android handset connected to an installed user-owned Windows host.
- Android only uses direct TCP/Noise and rejects circuit multiaddresses. Windows uses the approved direct authenticated transport and ordered direct TCP/QUIC fallback for one pinned peer identity. Relay remains disabled by ADR-0004.
- Direct connection refusal, absent/expired directory route and other transport failures are distinguished from invalid request/trust/identity rejection. Transport failure is surfaced as a typed network-unavailable result; diagnostics retain only safe stage/type categories and do not contain prompt or response contents.
- A future relay requires a new accepted decision, a working authenticated opaque-byte path and the approved multi-peer runtime acceptance. A control-plane reservation is not relay data-plane proof.

The physical-device AC-P2P-01 and independent deployment/reachability checks remain **NOT RUN**. Clean install and in-place upgrade are separate UPD-S1-021 gates.
